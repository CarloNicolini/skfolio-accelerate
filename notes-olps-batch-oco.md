I think the repository has a stronger conceptual value proposition than “make cross-validation faster.” After looking at the current skfolio-accelerate implementation and the current skfolio/MeanRisk workflow, I would formulate its role as a bridge between classical repeated batch portfolio optimization and genuinely online convex optimization.

The important point is that the repository already exploits part of the structure that OCO exploits, but at a different semantic level.

1. What skfolio-accelerate is actually doing today

The current accelerator recognizes that a WalkForward call such as

\text{fit}(X_{1:T_0}),\quad
\text{fit}(X_{2:T_0+1}),\quad
\ldots

does not consist of unrelated optimization problems.

For the supported MeanRisk subset, the training sets overlap heavily. The implementation therefore:

* updates empirical moments incrementally as windows move;
* constructs the CV execution plan once;
* keeps a fixed solver problem shape;
* reuses a compact OSQP or Clarabel engine;
* avoids repeatedly rebuilding CVXPY graphs and Python-side CV machinery. 

This is particularly effective for variance MeanRisk, where the repository reports 60–77× speedups on large WalkForward/MRC workloads because the same QP structure can be reused across hundreds of solves. Scenario-based MeanRisk gets smaller gains because Clarabel still has to rebuild more of the conic problem. 

So the essential abstraction is already:

\boxed{
\text{many nearly identical convex programs}
\quad\Rightarrow\quad
\text{one compiled numerical problem + changing data}
}

That is exactly the right direction.

⸻

2. But MeanRisk is still fundamentally a batch estimator

Suppose the simplest MeanRisk instance is

w_t
=
\arg\min_{w\in K}
\left[
\frac12 w^\top \Sigma_t w
-
\lambda \mu_t^\top w
+
R(w)
\right].

The important thing is that w_t is the solution of a statistical optimization problem built from the training sample.

For a rolling window,

\Sigma_t
=
\operatorname{Cov}(r_{t-N:t-1}),
\qquad
\mu_t
=
\operatorname{E}(r_{t-N:t-1}).

Then the next day comes along and the optimization problem becomes

\min_w
\frac12 w^\top \Sigma_{t+1}w
-
\lambda\mu_{t+1}^\top w+\cdots.

skfolio-accelerate recognizes that

(\mu_{t+1},\Sigma_{t+1})

can be obtained cheaply from

(\mu_t,\Sigma_t)

because only one observation leaves and one enters.

That is already a form of incremental optimization dataflow.

But the semantic object is still:

\boxed{
\text{new sample}
\rightarrow
\text{new empirical problem}
\rightarrow
\text{new optimizer solve}.
}

That is not yet OCO.

⸻

3. The OCO perspective changes one level of abstraction

In OCO you instead define a sequence of convex losses

\ell_t(w),

and the decision rule is

w_t = \mathcal A(\ell_1,\ldots,\ell_{t-1}),

with w_t chosen before observing \ell_t.

For portfolio selection using log loss,

\ell_t(w)=-\log(x_t^\top w),

and Exponentiated Gradient updates the current state according to the newly revealed gradient rather than recomputing the entire historical optimization. The uploaded OCO/portfolio references make this distinction explicit: the portfolio is selected sequentially and regret is measured against a comparator such as the best constant-rebalanced portfolio. 

So:

\boxed{
\text{MeanRisk/WF}
:
D_t\rightarrow P_t\rightarrow w_t
}

while

\boxed{
\text{OCO}
:
(w_t,\nabla\ell_t)\rightarrow w_{t+1}.
}

The first repeatedly solves a global empirical problem.

The second evolves a state.

⸻

4. And this makes the value proposition of skfolio-accelerate more interesting

I would reinterpret the current repository as sitting between these two worlds:

\text{Batch CVXPY}
\quad\longrightarrow\quad
\boxed{\texttt{skfolio-accelerate}}
\quad\longrightarrow\quad
\text{true OCO}.

Why?

Because the repository has already identified the computational invariant:

successive portfolio decisions are generated by optimization problems with enormous structural overlap.

Today, that overlap is exploited at the solver/data layer.

A natural next step is to exploit it at the optimization-algorithm layer.

That means replacing

P_t
=
\arg\min_{w} f_t(w)

being solved “from scratch,” even with a warm-started generic solver, by explicitly maintaining the state of the optimization algorithm across t.

⸻

5. Warm starting and OCO are related, but not identical

This distinction is crucial.

Suppose you solve

w_t=\arg\min f_t(w)

and then use w_t as the initial point for solving

w_{t+1}=\arg\min f_{t+1}(w).

That is warm-started sequential batch optimization.

It can be extremely effective because

f_{t+1}\approx f_t.

This is exactly the regime where the current accelerator is exploiting repeated solver structure.

But an OCO update says something stronger:

w_{t+1}
=
\arg\min_w
\left\{
\langle g_t,w\rangle
+
\frac1\eta D_\psi(w,w_t)
\right\}.

This isn’t merely “solve the next batch problem faster.”

It intentionally restricts the update to a local movement from w_t.

So there are really three levels:

\boxed{
\begin{aligned}
\text{Batch:}&\quad \text{solve }P_t\text{ independently},\\
\text{Warm-start batch:}&\quad \text{solve }P_t\text{ using }w_{t-1},\\
\text{OCO:}&\quad \text{define }P_t\text{ itself as an incremental update from }w_{t-1}.
\end{aligned}}

skfolio-accelerate is very naturally moving from the first toward the second.

The interesting research direction is moving from the second toward the third.

⸻

6. MeanRisk is actually a very good bridge to OCO

This is because many MeanRisk problems can be written in a form such as

\min_{w\in K}
f(w;\theta_t),

where \theta_t contains statistics estimated from a historical window:

\theta_t=(\mu_t,\Sigma_t,\text{scenario data},\ldots).

For example, a quadratic MeanRisk problem is approximately

f_t(w)
=
\frac12 w^\top \Sigma_t w
-\lambda \mu_t^\top w
+\rho\|w\|_2^2.

The current repository already makes

\theta_t\rightarrow\theta_{t+1}

cheap through incremental statistics.

The next question is:

Can we make \theta_t\rightarrow w_t cheap by exploiting the continuity of the optimization trajectory?

This becomes a parametric optimization problem:

w^\star(\theta_t).

Since consecutive \theta_t’s are close, the corresponding optimizers often lie close:

\|w^\star(\theta_{t+1})-w^\star(\theta_t)\|
\ll 1.

That is exactly the regime in which warm starts, Newton continuation, proximal continuation, predictor-corrector methods, and online optimization become powerful.

⸻

7. There is a particularly elegant mathematical connection

Consider quadratic MeanRisk:

w_t
=
\arg\min_{w\in K}
\frac12w^\top\Sigma_t w
-\lambda\mu_t^\top w.

Suppose we replace the exact historical objective by an incremental approximation:

w_{t+1}
=
\arg\min_{w\in K}
\left[
f_t(w_t)
+
\nabla f_t(w_t)^\top(w-w_t)
+
\frac{1}{2\eta_t}\|w-w_t\|_H^2
\right].

Then

w_{t+1}
=
\operatorname{prox}_{K,H}
\left(
w_t-\eta_tH^{-1}\nabla f_t(w_t)
\right).

This is now recognizably OCO / proximal mirror descent.

And if instead of the Euclidean metric we use a portfolio-appropriate metric,

D_\psi(w,w_t),

we obtain

w_{t+1}
=
\arg\min_{w\in K}
\left[
\langle g_t,w\rangle
+
\frac1{\eta_t}D_\psi(w,w_t)
\right].

EG is simply the entropy/simplex special case.

So the conceptual progression is:

\boxed{
\text{MeanRisk}
\rightarrow
\text{parametric convex optimization}
\rightarrow
\text{proximal continuation}
\rightarrow
\text{OCO}.
}

⸻

8. This suggests a much stronger interpretation of skfolio-accelerate

The repository is currently advertised as accelerating “large batch jobs.” 

I think the deeper proposition could eventually become:

Exploit temporal structure in convex portfolio optimization.

That is much broader.

There are at least three kinds of temporal structure:

Data structure

Instead of recomputing

\mu_t,\Sigma_t

from all observations,

maintain sufficient statistics incrementally.

The current repo already does this. 

Problem structure

Instead of rebuilding CVXPY’s computational graph,

keep the same symbolic problem and update parameters.

The current repo already does this for compact formulations. 

Solution structure

Instead of solving each instance as an isolated optimization problem,

maintain

w_t,\quad
\text{dual variables}_t,\quad
\text{factorizations}_t,\quad
\text{active set}_t,\quad
\text{preconditioner}_t

and update them as the problem evolves.

This is where the repository could evolve substantially beyond its current implementation.

⸻

9. ADMM makes the connection even more compelling

Suppose a MeanRisk problem has decomposition

\min_{w,z}
f_t(w)+g(z)

subject to

Aw+Bz=c.

ADMM performs iterative updates

w^{k+1}
=
\arg\min_w
f_t(w)
+
\frac{\rho}{2}
\|Aw+Bz^k-c+u^k\|^2,

z^{k+1}
=
\arg\min_z
g(z)
+
\frac{\rho}{2}
\|Aw^{k+1}+Bz-c+u^k\|^2,

u^{k+1}=u^k+Aw^{k+1}+Bz^{k+1}-c.

Now consider the WalkForward sequence:

f_t \rightarrow f_{t+1}.

Instead of restarting ADMM with

(w^0,z^0,u^0)

every day, carry over

(w_t,z_t,u_t)

as the initialization for the next problem.

Then the temporal dimension becomes part of the numerical algorithm.

You are effectively doing continuation in problem space.

For slowly changing financial data, this could be dramatically more powerful than merely warm-starting w.

The dual variables contain information about the active constraints. If the risk limit, sector constraint, turnover constraint, etc. remains active across neighboring folds, its dual state is an excellent predictor of the next solution.

That is something vanilla EG does not provide.

⸻

10. The key distinction from EG

This gives us a very useful hierarchy.

EG exploits temporal structure through a first-order update:

w_{t+1}
=
\Phi(w_t,g_t).

An accelerated MeanRisk solver could exploit temporal structure through the entire primal-dual state:

(w_t,z_t,y_t,\text{factorizations},\ldots)
\rightarrow
(w_{t+1},z_{t+1},y_{t+1}).

Hence the latter could preserve the full expressive power of MeanRisk:

\text{CVaR},
\quad
\text{EVaR},
\quad
\text{drawdown},
\quad
\text{semi-variance},
\quad
\text{conic constraints},
\quad
\text{factor constraints},
\ldots

while gaining something structurally similar to online learning.

The current repository already covers many of these MeanRisk risk measures and dispatches them to OSQP or Clarabel according to their problem class. 

That is arguably more general than simply implementing EG.

⸻

11. There is a particularly important point about previous_weights

The current skfolio API already distinguishes sequential problems in which the previous portfolio is economically relevant: transaction costs, turnover, previous-weight fallback, etc. Those currently remain on the native path in the accelerator because blindly reusing state could alter the investment problem. 

This is actually a clue toward the deeper architecture.

There are two notions of state:

\boxed{\text{economic state}}

such as previous holdings, and

\boxed{\text{numerical state}}

such as primal variables, dual variables, factorizations, active sets, etc.

A future online solver layer should preserve both, but not confuse them.

For example, with transaction costs,

\min_w
f_t(w)
+
\lambda\|w-w_{t}^{\rm held}\|_1,

the previous portfolio is part of the mathematical objective.

With an iterative solver, previous primal/dual variables are merely algorithmic state.

Keeping those concepts separate would be essential.

⸻

12. This also suggests a new way of thinking about WalkForward

Today:

\boxed{
\text{WalkForward}
=
\text{many independent empirical estimators}
}

even though they overlap statistically.

With the accelerator:

\boxed{
\text{WalkForward}
=
\text{one parameterized optimization trajectory}.
}

That is already a much better computational abstraction.

And ultimately:

\boxed{
\text{WalkForward}
\approx
\text{a discrete trajectory through a family of convex programs}.
}

Let

P(\theta_t)
=
\arg\min_w f(w;\theta_t).

Then the WalkForward backtest is sampling

w^\star(\theta_1),
w^\star(\theta_2),
\dots,
w^\star(\theta_T).

The fact that

\theta_{t+1}-\theta_t

is small is exactly why the trajectory can be tracked instead of independently solved.

This, in my opinion, is the strongest theoretical justification for the accelerator.

⸻

13. And this points to something potentially more interesting than “OCO support”

I would not make the end goal:

“Add EG to skfolio.”

That would actually be too narrow.

I would make the abstraction:

\boxed{
\textbf{Sequential Convex Optimization Engine}
}

with a hierarchy:

\text{statistics update}
\rightarrow
\text{parameter update}
\rightarrow
\text{warm-start / continuation}
\rightarrow
\text{incremental solver iterations}.

Then OCO becomes one possible policy over this engine.

You could support:

\begin{array}{ll}
\text{Batch} & w_t=\arg\min f_t(w)\\[2mm]
\text{Warm-started batch} & w_t=\operatorname{Solve}(f_t,w_{t-1})\\[2mm]
\text{FTRL} & w_t=\arg\min \sum_{\tau<t}\ell_\tau(w)+R(w)\\[2mm]
\text{OMD} & w_{t+1}=\operatorname{MirrorStep}(w_t,g_t)\\[2mm]
\text{Proximal OCO} & w_{t+1}=\operatorname{ProxStep}_K(w_t,g_t)\\[2mm]
\text{Primal-dual OCO} & (w_{t+1},y_{t+1})=\Phi(w_t,y_t,g_t).
\end{array}

All of these are exploiting the same underlying fact:

\boxed{\text{the next optimization problem is highly correlated with the previous one}.}

⸻

14. My assessment of the repository’s value proposition

I would therefore distinguish three layers.

Current value proposition

Make repeated skfolio CV/WalkForward substantially faster by exploiting overlapping data, fixed problem structure, and solver reuse.

This is already demonstrably true: the current repository reports very large gains for repeated variance MeanRisk solves and smaller but still meaningful gains for other supported formulations. 

Near-term technical value proposition

Turn WalkForward from a sequence of mostly independent solver invocations into a continuation problem, reusing not only the model structure but numerical state.

This means persistent primal/dual iterates, matrix factorizations, active-set information, adaptive penalty parameters, and solver-specific warm starts.

Long-term conceptual value proposition

Provide a general sequential convex optimization substrate in which classical skfolio estimators and OCO algorithms become two points on the same spectrum.

Then the architecture becomes:

\boxed{
\text{skfolio estimator}
\quad
\underset{\text{batch}}{\longleftrightarrow}
\quad
\text{sequential convex engine}
\quad
\underset{\text{online}}{\longleftrightarrow}
\quad
\text{OCO}.
}

That is, I think, much more profound than an accelerator library.

It says that WalkForward CV and Online Convex Optimization are not opposites. WalkForward is a particular way of generating a sequence of convex problems; OCO is a particular way of exploiting a sequence of revealed losses. skfolio-accelerate is already exploiting the fact that the resulting optimization problems are structurally correlated. The next step is to make that temporal correlation a first-class property of the solver itself.

And MeanRisk is almost ideal as the bridge because it gives you a rich family

f_t(w;\mu_t,\Sigma_t,\mathcal S_t,\ldots)

whose parameters evolve incrementally while the feasible set and conic/QP structure often remain fixed. The repository already recognizes exactly this structure at the compilation/moment level. 

The really interesting research question therefore becomes:

\boxed{
\textit{Can we track the optimizer }w^\star_t\textit{ through a nonstationary sequence of convex MeanRisk problems
with far fewer iterations than solving each problem independently?}
}

That question naturally leads to parametric convex optimization + warm starts + primal-dual continuation + OCO, rather than just “faster CVXPY.”
